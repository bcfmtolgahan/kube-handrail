# Changelog

All notable changes to kube-handrail are listed here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html) as described in [Releasing](docs/releasing.md). Each entry says whether the tool schemas changed (`enable-write` needed) and whether the agent guidance changed (`install-guidance` needed); `make upgrade` runs both when needed ([deploy](docs/deploy.md#upgrading)).

## [Unreleased]

Milestone 3: implemented and tested on a test cluster, except the test profile and `--reset-counters`, which are implemented but not yet run. Milestone 4 (legacy mode and the verify switch removed, `make upgrade`): implemented and tested on a test cluster (`make upgrade` from Milestone 3 took 110 seconds; the plan showed only the 12 moves and package rebuilds). Milestone 5 (CI tier 1): implemented; the integration suite runs on kind in CI on every pull request (about 2.5 minutes), and `e2e_gateway.py --live-only` passed on a test deployment. Tool schemas: unchanged, so no `enable-write`. Agent guidance: changed (`AGENTS.md` and both skills), so re-run `install-guidance` (`make upgrade` does). Milestone 6 (namespace policy, per-namespace approvers, rendered cluster manifests, plan-time admission check, the plan's cluster): implemented and tested on a test cluster with two namespaces (`make upgrade --with-k8s`, the admission cases in both namespaces, and the end-to-end run with `--with-namespaces` in client and server mode); the rendered admission policy and RBAC were checked on kind, and the integration suite runs on the rendered manifests. The tool schemas do not change in Milestone 6. Milestone 8 (schema release #1: HPA adjust, `change_ref`, the approval in `get_plan_outcome`): implemented and tested on kind (unit tests, the admission cases and the integration suite with metrics-server) and on a test cluster without metrics-server (`make upgrade` with one `enable-write`, the admission cases, the end-to-end run with `--with-hpa`); the live `both`-mode chat test is not done. This is the release's one tool schema batch: run `enable-write` and `install-guidance` (`AGENTS.md` and both skills); `make upgrade` runs both, with one kill-switch outage. Upgrade notes in [docs/history/upgrading.md](docs/history/upgrading.md). The named health checks planned for Milestone 8 are deferred ([roadmap](docs/roadmap.md#later-ideas)); no new error code.

### Changed

- **Shorter docs and agent context** (Milestone 7): `mcp/CONTRACT.md` keeps the tools, error table, plan record, guard order, limits, approval modes and configuration, with the rest in `mcp/contract/` appendices; `AGENTS.md` and both skills are shorter with the same rules, so re-run `install-guidance` (`make upgrade` does); a [quickstart](docs/quickstart.md); test logs under `docs/history/`. No schema change.
- **A scale plan for a Deployment an HPA targets names the HPA**: `conflict` with `details` `{hpa, hint: "use plan_adjust_hpa on <hpa>"}` (it had no `details` before) and the hint at the end of the message.
- Tool descriptions corrected in this schema batch: `plan_scale_deployment` no longer mentions the removed plan rate limit, and `verify_window_seconds` no longer says it is refused without verification (every apply is verified since Milestone 4).
- **GitOps ownership is detected by controller markers.** A Deployment is `gitops_managed` when it has the Argo CD annotation `argocd.argoproj.io/tracking-id` or a Flux kustomize-controller or helm-controller label (`kustomize.toolkit.fluxcd.io/name|namespace`, `helm.toolkit.fluxcd.io/name|namespace`). `app.kubernetes.io/instance` alone no longer counts: Helm sets it on every release, so every Helm-installed Deployment used to be refused. **Behaviour change:** if your Argo CD uses label tracking, set `gitops_markers = ["app.kubernetes.io/instance"]` before upgrading, or those objects become changeable through kube-handrail. Flux-managed objects, which were not detected before, are now refused.
- **Plan TTL by approval mode.** `plan_ttl_seconds` defaults to `null`: 900 seconds in `client` mode, where the human approves in the chat within the plan's own TTL, and 300 seconds in `server` and `both` mode. A value set in tfvars still wins. The TTL is not a guard; apply checks the live object again ([Guards](docs/guards.md#plan-lifetime)).
- `e2e_gateway.py` reads the values Terraform knows from `terraform output` of a test deployment (other states are ignored); set variables still win. Its `--approval-mode` defaults to the deployment's mode.
- **The gateway request interceptor and the verifier are always deployed.** Legacy mode (`caller_interceptor_enabled = false`) and the `verify_enabled` switch are gone: every plan names its agent, every caller of a write path must be a configured agent, and every apply is verified. The tool Lambdas require `AGENTS` and `AGENT_KILL_SWITCH_PREFIX` and do not start without them; a plan response always has `verification`; preflight no longer reports `agent_enabled` and `agent_budget` as skipped. The sentinel requires `EXPECT_INTERCEPTOR_ARN` and always checks the gateway's interceptor. On a deployment that had both enabled (the default) the upgrade is moves only for these resources; a deployment that had either off gets them in a two-step apply ([deploy](docs/deploy.md#upgrading)).
- `request_approval` in `client` mode still returns `invalid_argument`, with a clearer message: "client mode: apply directly, your client asks the human", followed by the previous message, so agents with the previous guidance still recognize it.
- The drift sentinel leaves the kill switch as it is when it already holds any value other than `true` (which is already off), instead of overwriting it with `false`; this keeps the marker `make upgrade` writes while the tool set changes.
- `e2e_gateway.py` runs the verification cases by default; `--skip-verify` leaves them out, and `--with-verify` is accepted and does nothing.
- The per-release upgrade notes moved to [Upgrade notes](docs/history/upgrading.md); [deploy](docs/deploy.md#upgrading) describes `make upgrade`.
- A correlation ID with a trailing newline is refused like any other value that is not a short token; it would have broken the User-Agent of every Kubernetes request. None of its sources is set by a caller.
- `audit.py export`: `summary.executed_by` is an object, `{attribution, queries}`, with CloudWatch Logs Insights templates for the Lambda logs (by plan ID and correlation IDs) and the EKS audit log (by User-Agent), instead of a fixed sentence. Milestone 9; tested on a test cluster.
- The audit-grade approver is documented as the server approval (`server` or `both` mode); `client` is an evaluation and convenience mode, because CloudTrail records a chat approval without the plan ID ([ADR 0002](docs/adr/0002-server-verified-approval.md#consequences), [deploy](docs/deploy.md#approval-mode)). `COMPLIANCE` is recommended for the audit bucket in production, with what it means for `terraform destroy` ([deploy](docs/deploy.md#audit-record-retention)).

### Added

- **HPA adjust** (Milestone 8, item 1; [Adjust HPA](mcp/contract/adjust-hpa.md#adjust-hpa), [appendix](mcp/contract/adjust-hpa.md)). `plan_adjust_hpa` and `apply_adjust_hpa` change a HorizontalPodAutoscaler's `min_replicas` and `max_replicas` (an omitted one stays) within the namespace's bounds, in namespaces whose `actions` list `adjust_hpa` (never a default). The blast radius applies to the pods the new bounds move (the Deployment's replicas clamped to them), recomputed at apply; the HPA's spec is pinned by hash (HPAs have no `metadata.generation`); `hpa_metrics_unavailable` warns when the HPA cannot read its metrics; the verification checks the HPA's `currentReplicas` within the bounds, `AbleToScale` and the Deployment's available pods; `revert_on_failure` patches both bounds back (the HPA then decides the pods). New plan record fields `target_kind`, `hpa_target`, `min_from`, `min_to`, `max_from`, `max_to`, `spec_from`, `spec_to` and the verify-only `revert_min_to`, `revert_max_to`; the breaker takes the direction of the bounds. No new error code.
- **HPA admission policy and RBAC.** `build/k8s/admission-policy.yaml` adds `kube-handrail-writer-hpa-bounds` (the writer's HPA bounds within the namespace's, `scaleTargetRef`, `metrics` and `behavior` frozen), checked at plan time for `plan_adjust_hpa`; the policy reader may get it. The writer gets `get` and `patch` on HPAs only where `adjust_hpa` is allowed, and Deployment `patch` only where scale, restart or rollback is.
- **`change_ref`** (Milestone 8; [appendix](mcp/contract/change-ref.md)): an optional ticket or incident reference on every `plan_*` and `apply_*` tool, at most 128 characters on one line, without control characters, line separators or spaces other than U+0020 (`invalid_argument` otherwise). It is pinned in `args_hash`, so apply must repeat it (`plan_mismatch`), and the approval view, the notification, `scripts/approve.py` and the audit summary show it as untrusted text.
- **`get_plan_outcome` reports the server approval**: `approval` `{status, approved_at}`, read-only and without the approver. In `both` mode `AGENTS.md` and the skills now wait for `approval.status` `approved` there instead of for a human's word.
- `scripts/audit.py verify` accepts the HPA adjust consume (`revert_min_to`, `revert_max_to`) and treats the HPA fields set at plan time as pinned; the audit summary also names `hpa_target`.
- `get_plan_outcome` adds `target_kind` and `hpa` for an HPA adjust; the approval view, the notification, `scripts/approve.py` and the audit summary show it. `e2e_gateway.py --with-hpa`; `tests/integration/test_kind_hpa.py` with metrics-server (`tests/integration/metrics-server.sh`, also in CI); HPA cases in `tests/admission/run.sh`.
- **Namespace policy** (Milestone 6). Terraform `namespaces` maps each namespace to its `min_replicas`, `max_replicas`, `actions` (`restart`, `rollback`, `scale`), `approvers` and `gitops_markers`. It ships in the tool Lambda and approver packages as `namespace_policy.json` (in their source hashes); `ALLOWED_NAMESPACES` is derived from it. An action the namespace does not allow is `forbidden_namespace` with `details` `{action, allowed_actions}`, on plan and apply; no new error code.
- **Per-namespace approvers.** A namespace with its own `approvers` is decided only by them (`forbidden`, `details.reason` `not_namespace_approver`, for anyone else, global approvers included); the others by `approver_principals`. The approver URL's permissions and Terraform's checks cover both lists.
- **Rendered cluster manifests** (`terraform/k8s.tf`, `terraform/modules/namespace-policy`): `build/k8s` holds per-namespace Roles and RoleBindings from the actions, one admission policy with the bounds of every namespace as CEL maps keyed by `request.namespace`, its binding in `admission_mode` (`Deny`, default, or `Warn`), and the ClusterRole `kube-handrail-policy-reader`. No kubernetes provider. Outputs `namespaces`, `k8s_manifests`, `namespace_label_command`.
- **Plan-time admission check.** Every plan reads the admission policy and its binding and is refused with `conflict` (`details.check` `admission_policy_match`) unless the binding denies, both select the namespace and the bounds match; an unreadable policy fails closed. Preflight lists `action_allowed` and `admission_policy_match`. Only `admission_check = false` (read Lambda `ADMISSION_CHECK`) turns it off.
- **The plan's cluster.** Plans record `cluster` (`CLUSTER_NAME`); the approval view, the notification ("Cluster: ..."), `get_plan_outcome`, the audit summary and `scripts/approve.py` show it.
- `make upgrade UPGRADE_FLAGS=--with-k8s` (`--kube-context`): writes `build/k8s`, applies it after a server-side dry run, checks the binding and lists Roles no longer rendered; `--k8s-only` runs just that against the deployed state. `make upgrade` runs `terraform get` before planning (by hand: `terraform get` or `init` once).
- `tests/k8s_render`: golden files for the rendered manifests, checked in CI without AWS. `tests/admission/run.sh` covers two namespaces with different bounds and the policy reader. `e2e_gateway.py --with-namespaces` (`SECOND_NAMESPACE`). `tests/integration` renders `tests/integration/namespaces.tfvars` and runs on those manifests and that `namespace_policy.json` with the admission check on (the CI job installs Terraform); it adds the namespace cases (`test_kind_namespaces.py`), and `admission_denied` is now a policy edited after the plan.
- **Integration suite on kind and moto** (`tests/integration`): the guard scenarios of the live end-to-end test, run with the Lambda handlers in process against a kind cluster, impersonating the `kube-handrail-reader` and `kube-handrail-writer` groups, with the admission policy in `Deny` and moto for DynamoDB (with the stream), SSM, SNS and S3 (with Object Lock). It covers the namespace and bounds, GitOps and HPA, single use and expiry, conflicts, kill switches, budgets, the breaker, blast radius, freezes, `admission_denied`, restart and rollback, forged callers, server approval, verification and revert, and the audit record ([coverage](tests/integration/README.md)). Skipped unless `KH_INTEGRATION` is set. `make integration` (`tests/integration/run.sh`) runs it on a throwaway `kh-int-*` cluster with its own kubeconfig.
- CI job `integration`: the suite on every push and pull request, on kind with the admission job's node image.
- `e2e_gateway.py --live-only`: only the cases the integration suite cannot cover (Cognito authentication, the gateway's schema check, applies through the real gateway, interceptor and EKS access entries, concurrent applies on real DynamoDB, the approval URL's IAM auth, and with `--with-identity` and `--with-audit` the identity and audit cases). Without it every case runs as before.
- `make upgrade` (`scripts/upgrade.py`): one resumable upgrade command. It refuses to start while the kill switch is off unless it turned it off itself, refuses a plan that deletes or replaces the gateway, its targets, Cognito, the plan table, the audit bucket or the kill switch and freezes parameters, applies known two-step migrations first, turns the kill switch off while the tool set changes, retries an "inconsistent final plan" once, runs `enable-write` and `install-guidance` only when needed, requires a sentinel `ok`, and ends with the smoke test. `--dry-run` stops after the plan check. Also `make bootstrap`, `deploy`, `register`, `smoke` and `destroy` (`scripts/cleanup.sh`).
- `scripts/smoke_test.py --read-only`: the read path only, for `server` and `both` mode.
- Outputs `gateway_id`, `approval_mode`, `devops_agent_space_id`, `devops_agent_association_id`, `tool_set_hash` and `cognito_user_pool_id`.
- `terraform/backend.tf.example`: remote state in S3 with a lock file.
- `gitops_markers` (Terraform) / `GITOPS_MARKERS` (Lambda environment): extra label or annotation keys that mark GitOps ownership.
- Validation: `plan_ttl_seconds` and `PLAN_TTL_SECONDS` at most 3600.
- Outputs `plan_ttl_seconds`, `guard_settings` and `dashboard_name`.
- A CloudWatch dashboard (with `sentinel_enabled`): plan and apply calls, guard rejections by code, tool errors, sentinel results, verifier runs, backlog and reverts, audit dead letters, failures and lag.
- `terraform/test.tfvars.example`, a test profile from the normal variables, and `e2e_gateway.py --reset-counters`, which deletes the current hour's apply counters on a test deployment only (a `name_prefix` with `test`, `e2e` or `ci` as a word).
- Guidance sync tests (`tests/unit/test_guidance_sync.py`, `scripts/check_contract.py`): the `AGENTS.md` tool and error tables and the `CONTRACT.md` error code line against `tools.json` and the error codes, tool and argument names in the skills, contract links, and word-count ceilings.
- `docs/releasing.md` and this changelog. Approval mode guidance and a shadow-mode recipe in [deploy](docs/deploy.md#approval-mode).
- **Milestone 9 (approver and executor identity, audit quality):** tested on a test cluster. Tool schemas: unchanged, so no `enable-write`. Agent guidance: unchanged. No Terraform change: `terraform plan` shows only package rebuilds (`terraform_data.build`) and in-place code updates of the Lambdas.
  - `approval_mode` on every plan record (the read Lambda's `APPROVAL_MODE`; a revert record copies its plan's), in the audit summary, `audit.py export` and `get_plan_outcome`.
  - `scripts/audit.py verify (<plan_id> | --since SECONDS | --all) [--json]`: flags attributes fixed at creation changed before the consume, a decision written, changed or undone outside the approval channel's one decision, a consume its own condition refuses (rejected, expired, created consumed), the executor-rewrite pattern (the consume writing more than its own fields, or after it a change beyond the result, verification and revert, or one of them written again), an invalid revert record, an apply on the wrong channel for the plan's approval mode, an apply without an unexpired server approval in `server` or `both` mode, missing creations, gaps, deletions and prefixes that are not plan ids, and exits 1 on any; `client`-mode applies are reported as `client_unobserved`, with a time window for CloudTrail, for information. The codes are in `audit.py verify --help` ([Export](mcp/contract/audit.md#export)).
  - Kubernetes API requests carry the User-Agent `kube-handrail/<version> plan/<plan_id> corr/<correlation_id>`, for matching against the EKS audit log. The version comes from `handrail_common.__version__`, which a unit test ties to `pyproject.toml` and the newest release here ([Releasing](docs/releasing.md#release-checklist)).

### Deprecated

- Terraform `sandbox_namespace`, `min_replicas` and `max_replicas` (now default `null`): replaced by `namespaces`. While `namespaces` is empty they still define the one namespace, with a warning (check `deprecated_namespace_variables`); together with `namespaces` they are refused. They will be removed in a later release.
- `k8s/sandbox/rbac.yaml` and `k8s/sandbox/admission-policy.yaml`: superseded by `build/k8s`; do not apply them. They will be deleted once the test harnesses that read them move.
- `plan_rate_limited`: never returned; it stays in the contract's error code list for this release only.
- Terraform `plan_rate_limit` and `plan_rate_window_seconds`: ignored, with a warning (check `deprecated_plan_rate`) while set. They will be removed in a later release.
- Terraform `caller_interceptor_enabled` and `verify_enabled`: ignored (default `null`), with a warning (check `deprecated_switches`) while set; `false` no longer turns anything off. Remove them from your tfvars; they will be removed in a later release.

### Removed

- The `sed` recipes for the RBAC and the admission policy in the deploy guide.
- Legacy mode and verification off: the `CALLER_INTERCEPTOR` and `VERIFY_ENABLED` Lambda environment variables, and the "verification is not enabled on this server" refusal.
- The per-object plan rate limit. A plan changes nothing, and every apply passes the cooldown, flapping and budget checks, so it added no safety. Preflight still lists `plan_rate`, as `{"passed": true, "skipped": true}`, for this release. The `plan_scale_deployment` tool description is corrected in the Milestone 8 schema batch.

### Upgrade notes (Milestone 6)

Implemented, not yet tested on a cluster.

1. `make upgrade UPGRADE_FLAGS=--with-k8s` with a kubeconfig for the cluster that may create Roles, a ClusterRole and the admission policy (cluster-admin). It prints the kubectl context before asking. Without `--with-k8s`, apply `build/k8s` yourself right after the upgrade (`kubectl apply --dry-run=server -f build/k8s/ && kubectl apply -f build/k8s/`): until then every plan is refused with `conflict` (`admission_policy_match`), because the read Lambda checks the new policy format through the new ClusterRole.
2. The ClusterRole `kube-handrail-policy-reader` is new: `get` on the admission policy and its binding only, bound to the reader group. It is the reader's first cluster-scoped right; review it.
3. Run the label command: `$(terraform -chdir=terraform output -raw namespace_label_command)`.
4. With `namespaces` empty nothing changes in the enforced policy (plans are still refused until `build/k8s` is applied, note 1): the deprecated variables define the same namespace and bounds, with every action, and the rendered binding is in `Deny`. The plan rebuilds the packages, updates every Lambda in place (the read Lambda gains `ADMISSION_CHECK`), creates `terraform_data.k8s_manifests` and changes outputs; Terraform warns while the deprecated variables are set. To move to `namespaces`, copy the entry the warning prints.
5. A deployment that kept its binding in `Warn` must either move to `Deny` (the default `admission_mode`) or set `admission_check = false`.

## History before this changelog

Releases before this file were not tagged. They are summarized by milestone; details are in the [roadmap](docs/roadmap.md).

- **Milestone 2: verified changes, more actions, accountable agents.** Restart and rollback by exact revision on a generic plan/apply framework; per-agent identity through a gateway interceptor, with per-agent budgets and kill switches; verification of every apply with an optional pre-approved revert (`get_plan_outcome`); change freezes; a ValidatingAdmissionPolicy that bounds the writer's replica changes; a write-once audit record in S3 with Object Lock.
- **Milestone 1: server-verified write path.** Spec-level conflict detection; the per-object oscillation breaker (cooldown, flapping, budgets, manual change); the drift sentinel and CI contract checks; the measured impact preview and blast-radius budget; server-side approval (`server` and `both` mode, `request_approval`, an IAM-authenticated approval API); correlation IDs and tool metrics; untrusted-output hygiene and `get_workload_events`; `AGENTS.md` and DevOps Agent skills; private-endpoint networking.
- **Milestone 0: vertical slice.** `get_workload_status` and a guarded `plan_scale_deployment` / `apply_scale_deployment` pair behind an AgentCore Gateway, with Terraform, namespace-scoped RBAC, end-to-end guard tests and AWS DevOps Agent registration.
