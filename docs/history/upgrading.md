# Upgrade notes

What to check, release by release, when upgrading a deployment; read every note between your version and the current one. `make upgrade` ([deploy](../deploy.md#upgrading)) runs the steps; [CHANGELOG.md](../../CHANGELOG.md) lists the changes.

## Milestone 3 and later

Oldest first; `make upgrade` runs the steps of each.

- **Interceptor and verifier always on** (the release after Milestone 3). `caller_interceptor_enabled` and `verify_enabled` are deprecated and ignored; Terraform warns (check `deprecated_switches`) while either is set, so remove them from your tfvars. On a deployment that had both enabled (the default), `terraform plan` shows 12 moves (`terraform_data.caller_key`, the interceptor's role, log group, role policy and function, and the verifier's role, log group, role policy, function, schedule rule, target and permission, each from `[0]`), rebuilds every package, updates every Lambda in place (the tool Lambdas also drop `CALLER_INTERCEPTOR` and `VERIFY_ENABLED` from their environment) and adds outputs. Any create or destroy of the interceptor, the verifier or their roles is a bug: stop and report it. A deployment with `caller_interceptor_enabled = false` or `verify_enabled = false` gets the missing resources; `make upgrade` creates the caller key, the interceptor and the verifier role first with `-target` (by hand: `terraform apply -target=terraform_data.caller_key -target=aws_iam_role.interceptor -target=aws_lambda_function.interceptor -target=aws_iam_role.verifier`, then `terraform apply`), because the tool Lambdas, the approver and the sentinel read them. The tool schemas do not change.
- **Namespaces and the admission check** (the release after Milestone 4). Run `make upgrade UPGRADE_FLAGS=--with-k8s` with a kubeconfig for the cluster (cluster-admin), or apply `build/k8s` right after `make upgrade`: until it is applied, every plan is refused with `conflict` (`admission_policy_match`), because the read Lambda now checks the new policy format and needs the new ClusterRole `kube-handrail-policy-reader`. With `namespaces` empty, `terraform plan` rebuilds every package, updates every Lambda in place (the read Lambda gains `ADMISSION_CHECK=true`; `ALLOWED_NAMESPACES`, `MIN_REPLICAS` and `MAX_REPLICAS` keep their values), creates `terraform_data.k8s_manifests`, changes outputs (`guard_settings` gains `namespaces`, `admission_mode`, `admission_check`; new `namespaces`, `k8s_manifests`, `namespace_label_command`) and warns about the deprecated variables if they are set. Any create, destroy or replace of anything else is a bug: stop and report it. The tool schemas do not change. The rendered policy for the deprecated variables equals the earlier one in effect (one namespace, the same bounds, every action) and its binding is in `Deny`; applying it replaces the earlier policy's variables and labels. Then run the label command (`terraform output -raw namespace_label_command`). Between the Terraform apply and the apply of `build/k8s` the new read Lambda refuses every plan (fail closed: `unreadable` while the ClusterRole is missing, `policy_modified` or `bounds_mismatch` against the earlier policy). To skip that window, render and apply the manifests before `make upgrade`; the earlier Lambdas ignore them and the rendered policy enforces the same bounds: `tests/k8s_render/render.sh terraform/terraform.tfvars /tmp/kh-k8s` (needs no credentials; the output directory also holds non-YAML files, so name the YAML files), then `kubectl apply --dry-run=server` and `kubectl apply` with `-f /tmp/kh-k8s/rbac.yaml -f /tmp/kh-k8s/policy-reader.yaml -f /tmp/kh-k8s/admission-policy.yaml`. Planning by hand needs `terraform -chdir=terraform get` (or `init`) once, for the new module.
- **Schema release #1: HPA adjust and `change_ref`** (Milestone 8). The tool schemas change (`plan_adjust_hpa`, `apply_adjust_hpa`, `change_ref` on every plan and apply tool, corrected descriptions), so `make upgrade` turns the kill switch off, runs `enable-write`, requires a sentinel `ok` and runs `install-guidance`. `terraform plan` replaces `terraform_data.build[*]` (the packages are rebuilt) and `terraform_data.k8s_manifests` (`build/k8s` gains the HPA policy and binding and the reader's `get` on them), and updates in place every Lambda (only the sentinel's environment changes: `TOOL_CLASSIFICATION` gains the two tools), both gateway targets (`tool_schema`), the read role's policy (`NeverApprove` gains `revert_min_to` and `revert_max_to`) and the dashboard; the outputs `tool_set_hash` and `k8s_manifests` change. Any other create, destroy or replace, in particular of a gateway target, the gateway, Cognito, the plans table or the audit bucket, is a bug: stop and report it (`make upgrade` refuses those). Apply `build/k8s` (`--with-k8s`): until then `plan_adjust_hpa` is refused (`conflict`, `admission_policy_match`), while the other plans keep working, because the Deployment policy does not change. Nothing changes for a namespace until its `actions` list `adjust_hpa`. Agents with the earlier guidance keep working: `change_ref` is optional.

## Before Milestone 4

The notes from before `make upgrade`, which now runs the steps they describe (the plan check, `enable-write`, the sentinel run, the kill switch, `install-guidance`, the smoke test); the notes say what to expect in the plan and what else to do by hand.

- **GitOps markers, plan TTL, plan rate limit and dashboard** (the release after Milestone 2; tested on a test cluster, where the plan matched this list). Before applying, check that `terraform plan` rebuilds every package (`terraform_data.build[...]`, because the shared code changed) and shows every Lambda as an update in place; only the two tool Lambdas also change their environment (`GITOPS_MARKERS` added, `PLAN_RATE_LIMIT` and `PLAN_RATE_WINDOW_SECONDS` removed, and in `client` mode `PLAN_TTL_SECONDS` from 300 to 900 when `plan_ttl_seconds` is not set). It adds `aws_cloudwatch_dashboard.this[0]` with the sentinel, and changes nothing on the gateway, its targets, the Cognito clients or the plan table. All new environment values come from variables, so they are known when the existing functions are planned.
  - **Helm releases are no longer GitOps-managed.** A Deployment with only `app.kubernetes.io/instance` can now be planned and applied. If your Argo CD uses label tracking, set `gitops_markers = ["app.kubernetes.io/instance"]` before this apply, or those objects become changeable through kube-handrail. Flux-managed objects are now refused with `gitops_managed`.
  - **Plan TTL.** `plan_ttl_seconds` now defaults to `null`: 900 seconds in `client` mode, 300 otherwise. A tfvars that sets `plan_ttl_seconds = 300`, as the old example did, keeps 300; remove the line to get the default. More than 3600 is refused. In `client` mode with `plan_ttl_seconds` unset and `approval_wait_ttl_seconds` below 900, `terraform plan` now fails the approver's precondition (the approval wait must cover the plan TTL); raise `approval_wait_ttl_seconds` or set `plan_ttl_seconds`.
  - **Plan rate limit removed.** `plan_rate_limit` and `plan_rate_window_seconds` are ignored, and Terraform warns (check `deprecated_plan_rate`) while they are set; remove them. Preflight still lists `plan_rate`, as skipped.
  - The tool schemas do not change (`tools.json` is the same), so the sentinel sees no drift and `enable-write` is not needed. Re-run `install-guidance`: `AGENTS.md` changed (the `gitops_managed` row, and `plan_rate_limited` is gone).
  - After the apply, run the smoke test, check that a client-mode plan's `expires_at - created_at` is 900, and open the dashboard.

- **Plan argument record.** Plans now store the arguments they cover (`args`). A plan made before this change has none: its apply and its approval are refused with `plan_expired`, and the agent plans again.
- **New tools** (`plan_restart_deployment`, `apply_restart_deployment`). Adding a tool changes the gateway's tool set before DevOps Agent's association knows it, so the drift sentinel reports drift and turns remediation off. With the DevOps Agent IDs configured, run `terraform apply`, then `scripts/devops_agent_register.py enable-write`, wait for a sentinel run that reports `ok`, then set the kill switch back to `true`. Re-run `install-guidance` so agents get the new `AGENTS.md` and the `kube-handrail-rollout` skill. The sandbox RBAC does not change: the writer's `patch` on Deployments covers the restart.
- **Agent identity** (Milestone 2, item 3). The caller interceptor is now on by default, and the write path fails closed without a verified caller. Before applying:
  - If `caller_interceptor_enabled` was `false`, the plan adds the interceptor Lambda, its role and log group, and changes the gateway's interceptor configuration. Check that the plan shows `aws_bedrockagentcore_gateway.this` as an update in place, not a replacement: a replaced gateway has a new URL, and DevOps Agent would have to be registered again.
  - The `agents` keys default to `devops_agent` and `smoke_test`, the keys of the existing Cognito clients, so the plan must show no change to `aws_cognito_user_pool_client.this[...]` and no change to the gateway's allowed clients. If you renamed or removed an agent key, its client is replaced or deleted.
  - Plans open during the upgrade name `mcp-gateway` and are refused (`forbidden`); the agent plans again. They expire within minutes anyway.
  - Create the caller key on its own first, then apply the rest:

    ```sh
    terraform -chdir=terraform apply -target=terraform_data.caller_key
    terraform -chdir=terraform apply
    ```

    The second apply sets `CALLER_KEY` on the interceptor and both tool Lambdas (an update in place). In a single apply the key is still unknown when the interceptor, which had no environment until now, is planned; the AWS provider then fails with `Provider produced inconsistent final plan` (`.environment: block count changed from 0 to 1`), and a second `terraform apply` completes it. A new deployment is not affected. While the apply updates them one by one, the interceptor and a tool Lambda can briefly disagree on the key; writes in that moment are refused with `agent_unknown`, and the agent plans again.
  - New on the first apply: the sentinel's `bedrock-agentcore:GetGateway` permission (if it were missing, every run would be `unknown` and the unknown-result alarm would fire) and the tool roles' `ssm:GetParameter` on `parameter/<prefix>/agents/*` (if it did not match, every agent would count as switched off). Both were confirmed on a test deployment. After the apply, run the smoke test and check that a plan's `requested_by` is `agent:smoke_test`, and wait for a sentinel run that reports `ok`.

  The tool set does not change, so the sentinel's association check sees no drift and `enable-write` is not needed. Re-run `install-guidance` so agents get the new error rows in `AGENTS.md`.
- **Rollback** (`get_rollout_history`, `plan_rollback_deployment`, `apply_rollback_deployment`). Re-apply the sandbox RBAC first: the writer gains `get` on ReplicaSets, which a rollback apply needs to re-read the ReplicaSet its plan pinned (`kubectl apply -f k8s/sandbox/rbac.yaml`, or the `sed` command above for another namespace). Without it a rollback apply fails with `kubernetes_error` after consuming its plan. Then add the tools as above: `terraform apply`, `scripts/devops_agent_register.py enable-write`, wait for a sentinel run that reports `ok`, set the kill switch back to `true`, and re-run `install-guidance` so agents get the new `AGENTS.md` and the extended `kube-handrail-rollout` skill.
- **Verification and revert** (Milestone 2, item 4). `verify_enabled` defaults to `true`. The apply adds a `verify-due` index to the plan table, the verifier Lambda with its role, log group, schedule and alarms, a new tool (`get_plan_outcome`), the `VERIFY_*` keys in both tool Lambdas' environments, the verifier role to the approver's refused principals, and the verification and revert attributes to the read role's deny of approval attributes. Before applying, check that `terraform plan` shows `aws_dynamodb_table.plans` as an update in place (the index is built online, and the table stays available), the tool Lambdas, the approver and the gateway targets as updates in place, and no change to `aws_bedrockagentcore_gateway.this` or `aws_cognito_user_pool_client.this[...]`. Terraform waits until the index is active before it creates the verifier; building the index can take several minutes. Then add the tool as above: `terraform apply`, `scripts/devops_agent_register.py enable-write`, wait for a sentinel run that reports `ok`, set the kill switch back to `true`, and re-run `install-guidance` so agents get the new `AGENTS.md` and skills. The sandbox RBAC does not change: the writer's `get` and `patch` on Deployments cover the verification and the revert. A DevOps Agent chat can keep reading the previous skill version for a while after `install-guidance` (on a test cluster, a chat started about half an hour later still got it, and one started after that got the new one); start a new chat to pick up the update, and check what the agent read in its journal if it does not know the new arguments.
  - Plans open across the upgrade can still be applied; their apply is verified with the default window. Records applied before it have no schedule, and `get_plan_outcome` reports them as `not_scheduled`.
  - After the apply, check that the index is `ACTIVE` (`aws dynamodb describe-table --table-name <prefix>-plans`), that the verifier logs one record per minute and the `<prefix>-verifier-stalled` alarm is `OK`, and that a plan's response has a `verification` block.
  - The end-to-end cases (`tests/e2e/e2e_gateway.py --with-verify`, with `--approval-mode server` in server mode) need `verify_window_min_seconds` of at most 60, and the operator's credentials need `ssm:PutParameter` on the kill switch, as for the other cases. They create a ResourceQuota `e2e-besteffort` in `kube-handrail-sandbox` that admits one BestEffort pod, only if the namespace has no LimitRange and no BestEffort pod, and delete it again; compare `kubectl get resourcequota,limitrange -A` before and after the run.
- **Change freezes** (Milestone 2, item 5). The apply adds the SSM parameter `/<prefix>/freezes` (value `[]`; later applies ignore its value), `FREEZES_PARAM` in both tool Lambdas' environments and `ssm:GetParameter` on the parameter in both tool roles. `FREEZES_PARAM` is built from `name_prefix`, so it is known when the existing functions are planned. Before applying, check that `terraform plan` shows the tool Lambdas and their role policies as updates in place, one new `aws_ssm_parameter.freezes`, and no change to the gateway, its targets or `aws_cognito_user_pool_client.this[...]`. The tool set does not change, so `enable-write` is not needed; re-run `install-guidance` so agents get the new `AGENTS.md` row and skill text.
  - If the role policy reached the Lambdas after their new environment, plans and applies are refused with `remediation_disabled` (`details.scope = "freezes"`, `unreadable`) until the policy is in place.
  - After the apply, run `scripts/freeze.py list` (it reads the `freezes_parameter` output) and the smoke test; a plan must still succeed with no freezes.
  - The end-to-end cases (`tests/e2e/e2e_gateway.py --with-freeze`, with `--approval-mode server` in server mode) need `FREEZES_PARAM` set to the `freezes_parameter` output and the operator's credentials need `ssm:GetParameter` and `ssm:PutParameter` on it. They add windows only for `kube-handrail-sandbox` and a namespace that does not exist on top of the stored freezes, never drop an operator's freeze, and always restore the stored value exactly. They refuse to run while a stored freeze covers `kube-handrail-sandbox`.
  - If `/<prefix>/freezes` already exists outside Terraform (created by hand), the apply fails with `ParameterAlreadyExists`: import it first (`terraform import 'aws_ssm_parameter.freezes' /<prefix>/freezes`) or delete it.
- **Admission policy** (Milestone 2). Nothing changes in Terraform or the Lambdas' environment. Deploy the write Lambda (it maps a refusal by the policy to `admission_denied`), re-run `install-guidance` so agents get the new `AGENTS.md` row and skill text, then roll out the policy in audit mode and switch it to `Deny` after the check ([Admission policy](../deploy.md#admission-policy)). On a cluster below 1.30 skip the policy; the rest works as before.
- **Audit record** (Milestone 2, item 6). `audit_enabled` defaults to `true`, so an existing deployment gets the record on its next apply. The apply turns on the plan table's stream (`NEW_AND_OLD_IMAGES`) and adds the audit bucket, the audit Lambda with its role, log group and event source mapping, the failures queue and, with the sentinel, four alarms; it also adds the audit role to the approver's refused principals (`DENIED_PRINCIPALS`, built from the role's name so it is known at plan time). Before applying, check that `terraform plan` shows `aws_dynamodb_table.plans` as an update in place (the stream is enabled on the live table, which stays available; the view type cannot be changed later without turning the stream off and on, which starts a new stream), the approver as an update in place, and no change to the tool Lambdas, the gateway, its targets or the Cognito clients. The tool set does not change, so `enable-write` and `install-guidance` are not needed.
  - **Object Lock mode.** `audit_object_lock_mode = "GOVERNANCE"` (the default) lets a principal allowed `s3:BypassGovernanceRetention` delete audit objects, which a test deployment needs to be torn down. For production set `COMPLIANCE`: then nobody, including the account root, can delete an object or the bucket before its retention ends. Object Lock cannot be turned off on the bucket. `audit_retention_days` (default 30) is the default retention of each object; changing it applies to objects written afterwards.
  - The mapping starts at `TRIM_HORIZON`, but a new stream holds only changes made after it was enabled: plans that already existed get entries from their next change on, without a creation entry (`has_creation: false` in the export).
  - After the apply, check that the event source mapping is `Enabled` (`aws lambda list-event-source-mappings --function-name <prefix>-audit`), make one plan, and run `scripts/audit.py export <plan_id>`: it should show a `created` entry within a few seconds.
  - **Tearing down a test deployment.** With GOVERNANCE, run `scripts/cleanup.sh` (it takes the bucket from `AUDIT_BUCKET`, else from the `audit_bucket_name` output in `TF_DIR`): it deletes every object version with the governance bypass before `terraform destroy`, which needs `s3:BypassGovernanceRetention` on the bucket. Alternatively set `audit_force_destroy = true` and apply before destroying; the provider then empties the bucket, which also needs the bypass permission. With COMPLIANCE, objects and the bucket stay until their retention has ended; `terraform destroy` fails on the bucket until then, and it can be removed from the state (`terraform state rm 'aws_s3_bucket.audit[0]'`) and deleted later. The stream mapping keeps running until `terraform destroy` removes it, so a plan record that expires in between writes one more object and destroy fails on the bucket (`BucketNotEmpty`); run the cleanup again.
  - **Turning the record off later.** `audit_enabled = false` destroys the bucket, the Lambda and the mapping, and turns off the plan table's stream. The bucket holds locked objects, so that apply fails on it like a teardown: under GOVERNANCE empty it first as above (or set `audit_force_destroy = true` and apply), under COMPLIANCE remove it from the state and keep it until its retention ends.
  - **Alarms need the sentinel.** The four audit alarms use the sentinel's alert topic and exist only with `sentinel_enabled`. Without it, a record that fails or reaches the failures queue is visible only in the audit Lambda's log and metrics and in the queue (`audit_dlq_url`).
  - The end-to-end cases (`tests/e2e/e2e_gateway.py --with-audit`, with `AUDIT_BUCKET` set) need the operator's `s3:ListBucket`, `s3:GetObject` and `s3:PutObject` on the bucket; they write nothing: the overwrite attempts are refused, and the one without `If-None-Match` carries an `If-Match` no object matches, so it cannot replace an entry even if the bucket policy were missing.

### From the Milestone 1 guide

- **Oscillation breaker.** The plan table gains the `object-history` index and its TTL attribute moves from `expires_at` to `retain_until`. DynamoDB cannot switch the TTL attribute in one step, so replace the table (it holds only short-lived plans; open plans must be made again): `terraform -chdir=terraform plan -replace=aws_dynamodb_table.plans -out=tfplan`, then apply it.
- **A new tool** (such as `get_workload_events` or `request_approval`). The tool set changes: with the DevOps Agent IDs configured, the sentinel reports `missing_tool` and turns the kill switch off. Run `enable-write` (or `associate-read` on a read-only association) right after `terraform apply`, wait for a sentinel `ok`, set the kill switch back to `true`, and start a new chat. Plans made before server-side approval cannot be requested or approved; plan again.
- **Correlation IDs.** Terraform sets `METRIC_NAMESPACE` on both tool Lambdas, adds `decision_correlation_id` to the read role's deny of approval attributes and creates the alarm. No RBAC change. Plans made before have no correlation IDs.
